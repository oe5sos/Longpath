## 0. Decisions carried from the design doc

1. **`SunSdrRadioConnection` is a third `RadioConnection` subclass, not a `TciClient` variant.** From the design doc's "Architecture mapping onto Longpath" section: *"Longpath already has the right shape for this — a `RadioConnection` subclass per wire protocol (`P1RadioConnection`, `P2RadioConnection`). A native SunSDR driver is a third: `SunSdrRadioConnection`, implementing the same interface, NOT a variant of today's `TciClient`"* — `TciClient` stays exactly what it is, a client of ExpertSDR2's companion protocol for people who don't want the native path.
2. **RX IQ feeds the same pipeline every other board uses.** Same section: *"RX IQ: feeds the same `FFTEngine`/`RxChannel` pipeline every other board uses — no parallel path, same principle as today's TCI panadapter wiring."* No new fork point is introduced by this plan.
3. **Receive-only for this pass, by design, not by omission.** Design doc "Phasing": step 2 is *"Connect + RX IQ + panadapter, receive-only, no PTT/drive code written at all yet. Bench-verified against real QRP hardware, same verification-matrix discipline as `2026-08-24-sunsdr-verification/`."* TX is its own later gate (Phasing step 5), explicitly requiring its own design pass and its own real QRP TX power sweep. This plan does not cross that gate; TX IQ pacing is called out in the design doc as *"new infrastructure, not a reuse of existing TX plumbing"* and is out of scope here entirely.
4. **The wire codec is already implemented and tested — this plan is the connection/session layer on top of it.** `SunSdrProtocol.{h,cpp}` already exists and has been tested against real captured bytes; this matches the design doc's "Confirmed from real QRP capture" section, which confirms the 18-byte control header and the 10-byte-header/1200-byte-payload IQ frame byte-for-byte against a real QRP (ports 50001/50002, magic byte `0x03`, `sunsdr_build_header`/`sunsdr_build_iq_header` layouts). This plan does not re-implement or re-verify that framing — it wires a `RadioConnection` subclass around it, including calling the already-existing `SunSdrProtocol::decodeIqSamples` in Phase D.
5. **The old SunSDR/KiwiSDR safety invariant does not apply here.** Design doc: *"The safety invariant from today's SunSDR/KiwiSDR work does not apply here — that invariant existed because SunSDR-via-TCI is a foreign accessory that must never touch a slice a real radio owns. A native SunSDR2 QRP driver isn't an accessory sharing a slice with something else — it is the real radio for that connection, the same standing as an ANAN. `RadioModel::connectToRadio()`'s normal path applies directly; no `suppressAutoStreamBinding` involved."* Nothing in this plan needs the `TciClient`'s echo-guard/slice-release machinery.
6. **Confirmed vs. still-open protocol facts are not the same thing, and this plan must not blur them.** Ports, magic byte, and both header formats are confirmed for the real QRP (design doc, "Confirmed from real QRP capture"). The boot-macro opcode-by-opcode *meanings*, the 68-byte STATE_SYNC template, and network reachability itself remain open — see §4. Phase C below is scoped around that boundary explicitly, not past it.

### Phase C — connect/session lifecycle: boot macro port + `rxWdspReady`-equivalent gate

**This phase cannot be completed as originally scoped, and that has to be said plainly rather than papered over.** Fresh research (2026-08-26) decoded ArtemisSDR's **DX-profile** 32-step boot macro (`sunsdr.c:2664-2711` — 3 bootstrap steps + 29 labeled steps, opcode/sub/delay for every one) in full. But the design doc's own "Confirmed from real QRP capture" section shows the *actual* QRP boot sequence is 92 control-channel packets whose opcode set is **richer than the DX table** — ten opcodes (`0x03, 0x04, 0x0c, 0x0d, 0x0f, 0x11, 0x12, 0x13, 0x16, 0x1c`) appear in the real capture with **no attributed meaning at all**, and the documented 68-byte STATE_SYNC template **was not observed anywhere in the capture**. So "port the DX macro's RX-relevant steps" is not yet a well-defined task for the QRP — the DX macro is a *reference shape*, not a confirmed QRP sequence.

## 3. Ordering / dependencies

- **A is a prerequisite for everything else** — the enum values (`ProtocolVersion::SunSdr`, the new `HPSDRHW` id) must exist before B, C, D, or E can compile against them.
- **B depends on A** but is otherwise independent of C and D — the skeleton, no-op setters, and threading-pitfall checklist don't need a live session.
- **C.1 is a hard blocking gate**, independent of A/B/E in code terms but blocking for C.2-C.4 and for any bench verification of D. C.3 (the `rxWdspReady`-equivalent gate) does **not** depend on C.1 — it's pure local state machinery and can be built and unit-tested in parallel.
- **D's skeleton (decode-and-emit wiring, unit test against a synthetic fixture) can proceed in parallel with C.1**, since it only needs the already-tested `SunSdrProtocol::decodeIqSamples` and a fixture built from the design doc's confirmed byte layout — it does not require opening a real session. Only D's *bench verification* waits on C.1/C.2.
- **E is independent of B/C/D's internals** but needs A.2's `HPSDRHW` id to exist first.
- **F depends on everything.**

Suggested sequence: **A → (B and E in parallel) → C.1 (bench, blocking) → C.2-C.4 → D's bench verification → F.** D's code-level skeleton can be written any time after A, in parallel with B/E, as long as it is not run live before C.1/C.2 land.

## 4. Open items this plan does not resolve

1. **The confirmed real QRP boot sequence does not structurally match ArtemisSDR's documented 32-step DX macro.** 92 real packets vs. 32 documented steps; ten opcodes present in the real capture (`0x03, 0x04, 0x0c, 0x0d, 0x0f, 0x11, 0x12, 0x13, 0x16, 0x1c`) have no attributed meaning at all; the documented 68-byte STATE_SYNC template was not observed anywhere in the capture. **Phase C cannot "port the boot macro" as originally scoped** — it can only proceed once targeted follow-up captures attribute these opcodes. This is the single biggest open item and the reason this plan schedules C.1 as a blocking, non-code bench step rather than skipping to C.2.
   **Update 2026-08-26:** a second, cleaner cold-launch capture (83 control packets — see design doc's dated finding) reproduces the same ten-unattributed-opcode gap even after cross-checking the freshly-cloned ArtemisSDR source directly (`../ArtemisSDR/`, commit `f8b01d2`, none of the ten are defined there either), and shows the connect sequence has the *shape* of a client state-sync burst (many query/reply pairs, no macro-style `Sleep()` pacing), not the DX macro's power-on shape — a different thing to port than "trim the DX macro," and still gated on isolated-action captures to attribute individually. The two `0x33`-magic 1218-byte outlier packets from the first capture reappeared identically in this one — a stable, repeatable part of the sequence, not a one-off.
2. **Whether the QRP has any STATE_SYNC-equivalent, and what shape it takes, is explicitly open** per the design doc — not a formality, a genuine unknown.
3. **The one-off 24-byte "board announce" frame and the two `0x33`-magic 1218-byte outlier packets remain unattributed.** A receiver-init/buffer-clear guess is offered in the design doc but explicitly flagged there as a guess, not a finding — this plan does not treat it as one either.
4. **Network reachability itself is unconfirmed, independent of the wire protocol.** Two bench sessions found the QRP unreachable at the ICMP/routing layer without an active ExpertSDR2 session running. The working hypothesis — the QRP's interface only fully comes up once an active ExpertSDR2 session has spoken to it — is explicitly labeled unconfirmed in the design doc, competing against an equally plausible WLAN/AP-side instability explanation (the same class of problem hit independently with the Anvelina on the same access point, twice more since — see this session's 2026-08-25/26 network troubleshooting). **If the "needs an active companion session" hypothesis is true, `SunSdrRadioConnection::connectToRadio()` may need to establish reachability itself, not just send the right bytes once reachable** — a new problem this plan's phases do not currently scope.
   **Update 2026-08-26:** the other half of this diagnostic ran opportunistically (ExpertSDR2 was already active for an unrelated bug bench-test): `sunsdr_probe` against the QRP with an active ExpertSDR2 session got network-layer reachability (ping replied) but zero protocol-layer replies on any profile. This confirms protocol-level exclusive session hold as real, but says nothing about reachability on its own — that half (QRP-on, ExpertSDR2 never launched) still stands unconfirmed at two-for-two "unreachable." See design doc's dated finding for the two-gates framing this splits into.
5. **Session-exclusivity behavior is unknown.** ArtemisSDR itself has no handling for "radio already claimed by another client" — there is no reference behavior to port for what a native driver should do if ExpertSDR2 already holds the control channel.
6. **The RadioInfo/ProtocolVersion extension (A.1) is assessed as low-risk from static analysis of usage sites only** — the one exhaustive switch and the equality/persistence usages were read, not built against. A genuinely new risk (an exhaustiveness check enforced somewhere the research didn't find, a UI enum-to-string table needing a new entry) could still surface only once the enum value is actually added and the project is built.
7. **`BoardCapabilities` has no existing precedent for a board that isn't an OpenHPSDR-family device at all.** Every existing row keys off `HPSDRHW` + `ProtocolVersion::Protocol1/2`. Minting a new `HPSDRHW` value for a non-HPSDR-wire radio, via the Andromeda/reserved-slot precedent, is a reasonable extrapolation — but it is an extrapolation. No existing row has ever represented a non-HPSDR protocol family, so other schema assumptions (the `protocol` field's downstream semantics, the sample-rate table shape, etc.) may not fit as cleanly as E.1/E.2 assume.
8. **There is no working SunSDR-specific probe fallback for the manual-connect path.** `AddCustomRadioDialog`'s existing probe is HPSDR-discovery-specific and inapplicable; separately, SunSDR's own `0x1A`/`0x12` identity queries got **no reply** in real bench testing on 2026-08-25 even while the QRP was confirmed reachable and in active use through TCI elsewhere. So A.4's "skip probe, save offline" is not a stopgap pending a working probe — right now, it is the only path there is, and an operator who mistypes the IP has no verification step to catch it.
9. **The manual-connect dialog/combo change is explicitly a UX/architecture decision, not pre-decided here.** Per `CLAUDE.md`'s AI boundary, A.4 above implements the mechanical minimum only; layout, icon, and flow decisions are left to the maintainer.
